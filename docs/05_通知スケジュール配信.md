# 通知スケジュール配信(Cloud Scheduler連携)

`/notifications` 画面では、即時配信(手動)に加えて**単発予約配信**と**繰り返し配信**(例: 毎週火曜18:00)を設定できる。
配信タイミングの管理はCloud Schedulerが行い、指定時刻にこの管理画面サーバー自身のAPIエンドポイントを呼び出す。
Cloud Functions等の別GCPリソースは使わない(既存のVPS + PM2構成のまま完結する)。

## 全体の流れ

```
管理画面で通知を保存
  → バックエンドがMongoDBに保存 + Cloud Scheduler APIでJobを自動作成/更新/一時停止/削除
  → 指定時刻にCloud SchedulerがHTTPS経由でこの管理画面の
    /api/notifications/dispatch/[id] を呼び出す
  → エンドポイントがMongoDBから最新の本文・有効/無効を取得し、有効ならFCM送信
```

管理者がGCPコンソールのCloud Scheduler画面を直接操作することは想定していない。Job管理は全て
`lib/scheduler.ts` がAPI経由で自動的に行う。

## 事前準備(GCPプロジェクト側で1回だけ、人手で行う設定)

1. 対象のGCPプロジェクト(Firebaseプロジェクトと同一)で **Cloud Scheduler API** を有効化する
2. `FIREBASE_SERVICE_ACCOUNT_KEY` に設定しているサービスアカウントに `roles/cloudscheduler.admin` を追加付与する
   (IAM & 管理 > IAM でそのサービスアカウントのメールアドレスを検索し、ロールを追加)
3. `.env` に以下を追記する(`docs/02_環境変数リファレンス.md` も参照)
   - `GCP_SCHEDULER_LOCATION`(例: `asia-northeast1`)
   - `NOTIFICATION_DISPATCH_BASE_URL`(本番は`AUTH_URL`と同じ値、例: `https://hapiken.jp/admin`)
   - `NOTIFICATION_DISPATCH_SECRET`(`openssl rand -base64 32` で生成)
4. `pm2 restart hapiken-admin --update-env` で反映

## Notificationモデルのフィールド(スケジュール関連)

| フィールド | 用途 |
|---|---|
| `scheduleType` | `immediate`(手動)/`once`(単発予約)/`recurring`(繰り返し) |
| `enabled` | 有効/無効。スケジュール系のみ意味を持つ。無効化するとCloud SchedulerのJobが`PAUSED`になる |
| `scheduledAt` | `once`の配信日時 |
| `recurrence.daysOfWeek` / `recurrence.time` | `recurring`の配信曜日(0=日〜6=土、複数可)と時刻(`HH:mm`、Asia/Tokyo固定) |
| `cronExpression` | 生成されたcron式(表示・デバッグ用) |
| `schedulerJobName` | 対応するCloud SchedulerジョブのフルリソースID |
| `lastDispatchedAt` | 直近の自動配信日時 |

## 設定変更時の挙動

| 変更内容 | 実際に起きること |
|---|---|
| 本文のみ変更 | MongoDB更新のみ。Cloud Scheduler Jobは変更しない。次回発火時に新しい本文が使われる |
| 配信日時/曜日/時刻を変更 | MongoDB更新 + Cloud Scheduler Jobの`schedule`を`updateJob`で更新 |
| 無効化 | Cloud Scheduler Jobを`pauseJob`で一時停止(削除はしない) |
| 有効化 | Cloud Scheduler Jobを`resumeJob`で再開(未作成なら新規作成) |
| 削除 | Cloud Scheduler Jobを`deleteJob`で削除してからMongoDBのドキュメントを削除 |
| 単発予約が発火した後 | `/api/notifications/dispatch/[id]`がFCM送信後、自分自身のJobを削除する(翌年の同日同時刻に誤発火しないように) |

## 動作確認手順

1. 管理画面で単発予約通知を数分後の時刻で作成する
2. MongoDBの`notifications`コレクションで、対象ドキュメントに`schedulerJobName`と`cronExpression`が入っていることを確認する
3. GCPコンソールのCloud Scheduler画面、または `gcloud scheduler jobs describe <job名> --location=<location>` でJobが作成されていることを確認する
4. 実際の発火を待つか、`gcloud scheduler jobs run <job名> --location=<location>` で手動発火させる
5. `pm2 logs hapiken-admin` でエラーが出ていないことを確認する
6. 実機(iOS/Android)でPush通知が届くことを確認する
7. 本文のみ編集 → Jobのscheduleは変わらないこと、次回発火時に新しい本文が届くことを確認する
8. 曜日/時刻を編集 → Jobの`schedule`が更新されることを確認する
9. 無効化 → Jobが`PAUSED`になることを確認する。有効化で`ENABLED`に戻ることも確認する
10. 削除 → Jobが削除されることを確認する

## ローカルでの動作確認

### `.env`準備時の注意(プレースホルダの置き換え忘れ)

`cp env.example .env` した直後は、以下のように**値の一部だけプレースホルダが残っている**フィールドがある。
「値は入っているから大丈夫」と見えてしまうため見落としやすい。

```env
# env.example のまま(NG例)
ADMIN_MONGODB_URI=mongodb+srv://<user>:<password>@<cluster>.mongodb.net/app-admin
AUTH_SECRET=<ここに32文字以上のランダム文字列>
```

`ADMIN_MONGODB_URI`をこのままにして起動すると、`<cluster>.mongodb.net`という存在しないホスト名を
DNS解決しようとして次のエラーになる(実際に発生した例)。

```
querySrv EBADNAME _mongodb._tcp.<cluster>.mongodb.net
```

`AUTH_SECRET`も同様にプレースホルダのままだとログインできない。どちらもMongoDB Atlasの実際の接続文字列・
`openssl rand -base64 32`で生成した値に置き換えること。

### GCP側の事前設定(コンソールで1回)

「事前準備」章の1・2(Cloud Scheduler API有効化、サービスアカウントへの`roles/cloudscheduler.admin`付与)を
先に済ませておく。`.env`の`NOTIFICATION_DISPATCH_BASE_URL`はローカルでJobの**作成だけ**を確認するなら
`http://localhost:3000/admin`のままでよい(GCPはJob作成時にURLへの疎通確認をしないため)。実際に発火させて
このローカルサーバーまで届くか確認したい場合は、`ngrok http 3000`等で一時的に公開したURLに差し替える。

### `gcloud` CLIでの確認コマンド

```bash
# 対象プロジェクトを指定(FIREBASE_SERVICE_ACCOUNT_KEYのproject_idと同じ値)
gcloud config set project <project-id>

# Job一覧
gcloud scheduler jobs list --location=asia-northeast1

# 特定Jobの詳細(schedule/timeZone/httpTarget.uri/次回実行時刻などを確認)
gcloud scheduler jobs describe notif-<通知のMongoDB ID> --location=asia-northeast1

# 指定時刻を待たずに即時発火(ローカルの場合はNOTIFICATION_DISPATCH_BASE_URLが
# 外部から到達できるURLになっていないと、GCP側からの呼び出しは失敗する)
gcloud scheduler jobs run notif-<通知のMongoDB ID> --location=asia-northeast1

# 一時停止/再開(管理画面の無効化/有効化と同じ操作をCLIから行う場合)
gcloud scheduler jobs pause notif-<通知のMongoDB ID> --location=asia-northeast1
gcloud scheduler jobs resume notif-<通知のMongoDB ID> --location=asia-northeast1

# 削除
gcloud scheduler jobs delete notif-<通知のMongoDB ID> --location=asia-northeast1
```

GCPコンソールでの確認は https://console.cloud.google.com/cloudscheduler を開き、上部のプロジェクト選択が
`FIREBASE_SERVICE_ACCOUNT_KEY`と同じプロジェクトになっていることを確認した上で一覧を見る。

## トラブルシューティング

- `/api/notifications/dispatch/[id]` が401を返す: `NOTIFICATION_DISPATCH_SECRET` の値がCloud Scheduler Job側の
  `Authorization`ヘッダーと一致しているか確認する(Jobを作り直せば管理画面側が保持する最新の値で再設定される)
- Jobの作成/更新時にエラーになる: サービスアカウントに`roles/cloudscheduler.admin`が付与されているか、
  `GCP_SCHEDULER_LOCATION`が正しいリージョン名か確認する
- 単発予約が翌年また発火する: `dispatch`エンドポイントでのJob自己削除に失敗している可能性がある。
  ただし`enabled`かつ`status !== "sent"`のガードがあるため、二重送信自体は発生しない
