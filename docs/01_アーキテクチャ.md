# アーキテクチャ

はぴけんは **2つの独立したリポジトリ** で構成されている。プロセス間の直接通信は無く、
唯一の橋渡しは MongoDB を共有していること。

```
┌─────────────────────────┐         ┌──────────────────────────────┐
│  care (アプリ + API)     │         │  admin-dashboard（本リポジトリ）│
│  Shohei2000/care          │         │  MomozakiRyoya/hapiken-admin   │
│  Express + Socket.IO      │         │  Next.js 16 App Router          │
│                          │         │                                │
│  care 本体のDB書き込み ───┼───┐   │                                │
└─────────────────────────┘   │   │                                │
                                │   │  ┌──────────────┐              │
                                └──►│  │ APP_MONGODB_URI│ 読み取り専用 │
                                    │  └──────────────┘              │
                                    │  ┌──────────────┐              │
                                    │  │ADMIN_MONGODB_URI│管理画面自身│
                                    │  └──────────────┘              │
                                    └──────────────────────────────┘
```

care の本番プロセス名・デプロイ手順は care リポジトリの `docs/04_デプロイセットアップ/` を参照。

## MongoDB 2接続の設計

`lib/db.ts` に2つの接続関数がある。

| 関数 | 接続先 | 未設定時の挙動 | 用途 |
|---|---|---|---|
| `connectDB()` | `ADMIN_MONGODB_URI`（mongoose デフォルト接続、キャッシュ有り） | **例外を投げる**（`throw new Error(...)`） | 管理画面自身のデータ（後述の11モデル） |
| `connectAppDB()` | `APP_MONGODB_URI`（`createConnection` による別接続） | **`null` を返す**（例外にならない） | care 側 `users` / `healthlogs` などのコレクションの読み取り（書き込みは下記の例外のみ） |

`connectAppDB()` が `null` を返すケースは呼び出し側（`app/api/customers/*`, `app/api/dashboard/*`,
`app/api/export/*`, `app/api/analytics/*`）で個別にハンドリングされている。**未設定でもビルド・起動は
通るが、顧客管理・分析系の画面が空表示になる。**

> **例外**: `CommonCalorieItem`（`commoncalorieitems` コレクション）のみ、APP側DBに対して
> 管理画面から**書き込み（作成・更新・削除）を行う**（`app/api/common-calorie-items/*`）。
> 食事データは運用担当が管理画面から直接精査・修正する運用のため、意図的に
> read-only 方針の例外としている。care 本体側の実装・整合性に影響する可能性があるため、
> このコレクションに変更を加える場合は care 側の利用箇所も確認すること。

> **例外（顧客）**: 顧客詳細画面からの操作に限り、`users` へ書き込む。ポイント手動変更
> （`buddyPoints` の加減算、`PATCH /api/customers/[id]`）と、顧客の削除（`DELETE /api/customers/[id]`）である。
> 削除は `lib/app-user-deletion.ts` が、アプリの退会処理（care/server/routes/user.ts の `DELETE /profile`）と
> 同じ範囲（`healthlogs` / `achievements` / `dashboardstats` / `conversations` / `chatmessages` と `users` 本体）を消す。
> `users` から消えるので、同じメールアドレスでアプリから再登録できる。ADMIN 側の `PointTransaction` と、
> APP 側のそれ以外のコレクション（`buddypointlogs` など）は残る。退会処理の削除範囲を変えたら、こちらも揃えること。
> 削除は取り消せないため、実行できるのは `SUPER_ADMIN` だけ（ポイント手動変更は `WRITE_ROLES`）。
> 削除の直前に、退会の記録を `userwithdrawals` へ1行書く（`lib/app-user-withdrawal.ts`、userId で一意）。
> 書けなかったときは削除しない。顧客分析の「退会ユーザー数」はこの記録を数える。

## オンライン判定の仕組み

1. care/server が Socket.IO で JWT ハンドシェイク検証・接続参照カウントを行い、ユーザーの
   `users.isOnline` / `users.lastSocketAt` を更新する（起動時に `isOnline` を一括リセット、
   60秒ごとのスイープで整合性を取る。実装詳細は care リポジトリ側を参照）。
2. 管理画面側は `AppUser` モデル経由でこの2フィールドを読み取るのみで、書き込みは行わない。
3. `lib/presence.ts` の `isUserOnline()` が最終判定を行う。`isOnline === true` かつ
   `lastSocketAt` が **3分以内**（`ONLINE_FRESH_MS`）なら online とみなす。

   ```ts
   // lib/presence.ts
   export const ONLINE_FRESH_MS = 3 * 60 * 1000;
   ```

   この3分という鮮度しきい値は、care/server 側の60秒スイープ間隔より意図的に長く取ってある。
   care/server がクラッシュして `isOnline: true` のまま更新が止まっても、3分経てば
   管理画面側は自動的にオフライン扱いに切り替わる（自己修復設計）。

## 認証（NextAuth v5）の落とし穴

このプロジェクトで実際に発生した詰まりどころ。**新エンジニアが同じ罠にはまらないよう必ず読むこと。**

1. **ログインは Server Action のみ**（`app/(auth)/actions.ts` → サーバーサイドの `signIn`
   （`@/auth` からインポート）を呼ぶ）。`next-auth/react` の `signIn()` は CSRF エラーで
   `/api/auth/error` に飛ぶため使わない。
2. **`SessionProvider`（`next-auth/react`）は使わない**。v5 には `/api/auth/session`
   エンドポイントが存在せず、`SessionProvider` がこれを定期ポーリングして `UnknownAction`
   エラーが連発しログイン不能になる。代わりに `app/session-context.tsx` のカスタム Context に
   サーバーの `auth()` 結果をそのまま渡している（`app/providers.tsx` 経由）。
3. **`AUTH_TRUST_HOST` はコードで強制的に `"true"` に上書きされる**（`auth.ts:8` と
   `next.config.ts` の両方）。`.env` に書いても無視されるので設定不要（[`env.example`](../env.example)
   にも注記あり）。
4. **`AUTH_URL` には basePath `/admin` を含める**（例: 本番 `https://hapiken.jp/admin`）。
   `app/(auth)/actions.ts` の `redirectTo: process.env.AUTH_URL || "/admin"` で使われる。
   含め忘れると NextAuth が basePath なしの誤ったURLへリダイレクトする。ローカル開発は
   未設定でも相対パス `/admin` にフォールバックするので気づきにくい。
5. **`proxy.ts` は `matcher: []` で実質無効化されている**（ロジック自体は書かれているが
   一度も実行されない）。実際の認証チェックは `app/(dashboard)/layout.tsx` の
   `if (!session?.user) redirect("/login")` で行われている。
6. Nginx 側で `/api/auth/` → `/admin/api/auth/` への rewrite が必要（本番のみ。
   詳細は [`03_本番反映手順.md`](03_本番反映手順.md)）。

## ログインのセキュリティ挙動（`auth.ts`）

- Credentials プロバイダ + bcrypt によるパスワード照合
- **5回ログイン失敗で30分間ロックアウト**（`Admin.lockedUntil`）
- 2FA は otplib（TOTP）+ qrcode で実装（`app/api/auth/setup-2fa/route.ts`）
- セッション戦略は JWT（`session: { strategy: "jwt" }`）。`role` は JWT トークンに含めて
  `session.user.role` として参照する
- ログイン成功・失敗は `AuditLog` に記録される
